# Архитектурное решение по кешированию

## Мотивация

Симптомы проблемы:
- операторы MES жалуются на медленную загрузку первой страницы и списка заказов;
- клиенты недовольны скоростью выполнения заказа, так как операции в производственном контуре обрабатываются с задержками;
- при росте числа заказов увеличивается нагрузка на MES API и MES DB, что ухудшает время ответа и стабильность.

Почему необходимо внедрить кеширование:
- сейчас много повторяющихся операций чтения (списки заказов, карточка заказа, справочники статусов/этапов), которые каждый раз идут в БД;
- "тяжелые" выборки на страницу операторов конкурируют с транзакционными запросами изменения статусов;
- снижение нагрузки на БД позволит уменьшить latency API и ускорить пользовательские сценарии без полного рефакторинга.

Какие элементы включаем в кеширование в первую очередь:
1. Список заказов для страницы операторов MES (фильтры: статус, дата, приоритет, страница).
2. Карточка заказа по `order_id`.
3. Справочники и редко изменяемые данные (этапы производства, статусы, правила отображения).
4. Агрегированные счетчики для дашборда операторов (кол-во заказов по статусам).

Целевые эффекты:
- ускорение `GET /mes/orders` и связанных запросов (P95/P99);
- снижение нагрузки на MES DB (CPU, IOPS, количество тяжелых select);
- уменьшение времени реакции операторов и сокращение цикла обработки заказа;
- более стабильная работа системы в часы пиков.

## Предлагаемое решение

### Кешировать какую часть системы
Кеширование внедряется в контур MES:
- серверный кеш в MES API для чтения списка заказов и карточек;
- кеш справочников в MES API;
- опционально: HTTP-кеш для фронтенда операторов на короткое время для неизменяемых ответов.

Основной узкий участок - чтение в MES. Поэтому приоритетно кешируются read-сценарии MES, а не весь контур целиком.

### Какой тип кеширования выбираем
**Основной выбор: серверное кеширование** (Redis + локальный in-memory кеш в MES API для микрокеша).

Почему серверное:
- данные общие для многих операторов, нужен единый кеш для всех инстансов API;
- можно централизованно управлять TTL, инвалидацией и наблюдаемостью;
- клиентский кеш у операторов не решит конкуренцию за ресурсы БД и не гарантирует консистентность между пользователями.

Клиентское кеширование можно использовать как дополнительное (краткий TTL для статики/справочников), но не как основное.

### Паттерн кеширования
Для операций чтения списка заказов и карточки заказа выбран **Cache-Aside**:
1. API сначала читает из Redis по ключу.
2. При `cache miss` читает из MES DB.
3. Записывает результат в Redis с TTL.
4. Возвращает ответ клиенту.

Почему Cache-Aside:
- простая реализация без сильной связанности БД и кеша;
- хорошо подходит для read-heavy сценариев, где есть "горячие" ключи;
- позволяет тонко управлять TTL и точечной инвалидацией.

Почему не Write-Through как основной:
- усложняет write-поток и увеличивает задержку на запись;
- для MES критичнее быстрое и надежное изменение статуса в БД, чем мгновенная синхронная запись в кеш;
- требует жесткой дисциплины записи только через слой кеша.

Почему не Refresh-Ahead как основной:
- требует точного прогнозирования "горячих" ключей;
- может прогревать ненужные данные и увеличивать инфраструктурную стоимость;
- лучше использовать точечно для дашбордов, но не для всего каталога заказов.

### Стратегия инвалидации кеша
Используем **гибридную стратегию**: `по ключу + TTL + программная`.

1. Инвалидация по ключу (основная):
   - при изменении статуса заказа инвалидируем:
     - `mes:order:{order_id}`
     - все затронутые ключи списка `mes:orders:list:*` (через version tag или index-set ключей).

2. TTL (страховочная):
   - список заказов: 15-60 секунд (зависит от фильтра);
   - карточка заказа: 30-120 секунд;
   - справочники: 10-60 минут.

3. Программная инвалидация:
   - при массовых операциях (батч обновления, релиз, миграция) выполняем принудительный purge по префиксам.

Почему подходит:
- ключевая инвалидация дает актуальность сразу после изменения статуса;
- TTL защищает от "зависших" ключей и ошибок инвалидации;
- программный purge закрывает операционные кейсы.

Почему только временная инвалидация хуже:
- при коротком TTL растет нагрузка на БД;
- при длинном TTL операторы видят устаревшие статусы.

Почему только программная хуже:
- слишком высокая зависимость от ручных действий/процедур;
- риск человеческой ошибки и несвоевременной очистки.

### Последовательность действий для Sequence Diagram

#### 1) Чтение списка заказов (операторская страница MES)
Участники:
- Operator UI
- MES API
- Redis Cache
- MES DB

Шаги:
1. `Operator UI -> MES API`: запрос `GET /mes/orders?status=...&page=...`.
2. `MES API -> Redis`: `GET mes:orders:list:{hash(filters,page,sort)}`.
3. Если `cache hit`:
   - `Redis -> MES API`: список заказов;
   - `MES API -> Operator UI`: ответ 200.
4. Если `cache miss`:
   - `MES API -> MES DB`: SQL на выборку заказов;
   - `MES DB -> MES API`: результат;
   - `MES API -> Redis`: `SET key value EX ttl`;
   - `MES API -> Operator UI`: ответ 200.
5. (Опционально) Асинхронно: `MES API -> Metrics/Logs`: запись hit/miss и latency.

#### 2) Изменение статуса заказа
Участники:
- Operator UI
- MES API
- MES DB
- Redis Cache
- Event Bus (RabbitMQ, опционально)

Шаги:
1. `Operator UI -> MES API`: `PATCH /mes/orders/{order_id}/status`.
2. `MES API -> MES DB`: транзакционное обновление статуса заказа.
3. `MES DB -> MES API`: commit ok.
4. `MES API -> Redis`:
   - `DEL mes:order:{order_id}`
   - `DEL/INCR_VERSION mes:orders:list:*` (инвалидация списков).
5. `MES API -> RabbitMQ` (опционально): событие `order_status_changed` для downstream систем.
6. `MES API -> Operator UI`: ответ 200 с новым статусом.

### Сравнительный анализ вариантов

| Критерий | Решение 1: Redis + Cache-Aside (выбранное) | Решение 2: Только клиентский кеш (браузер/UI) |
|---|---|---|
| Где хранится кеш | Серверный централизованный кеш | У каждого клиента локально |
| Влияние на MES DB | Сильно снижает read-нагрузку | Почти не снижает общую серверную нагрузку |
| Консистентность между операторами | Управляемая (инвалидация + TTL) | Слабая, разные клиенты видят разные данные |
| Сложность внедрения | Средняя (Redis, ключи, инвалидация) | Низкая/средняя |
| Масштабирование | Хорошее, общий кеш для всех API-инстансов | Ограничено клиентским поведением |
| Риски | Ошибки инвалидации, прогрев кеша | Устаревшие данные на рабочих местах |
| Пригодность для MES | Высокая | Низкая как самостоятельное решение |

Дополнительно по паттернам:

| Критерий | Cache-Aside (выбран) | Write-Through | Refresh-Ahead |
|---|---|---|---|
| Нагрузка на запись | Низкая | Выше (запись и в БД, и в кеш) | Средняя |
| Актуальность после write | Высокая при key invalidation | Высокая | Зависит от расписания |
| Простота внедрения | Высокая | Средняя | Средняя/высокая |
| Риск лишней работы | Низкий | Средний | Высокий (прогрев ненужных ключей) |
| Fit для MES read-heavy | Лучший | Хороший, но дороже в write-path | Хороший точечно, не базово |

### Заключение
Оптимальный базовый вариант для текущих проблем MES: **серверное кеширование Redis + Cache-Aside + гибридная инвалидация (по ключу + TTL + программная)**.

Почему:
- максимально быстро снижает read-нагрузку на MES DB;
- ускоряет страницу операторов и массовые read-запросы;
- сохраняет контролируемую актуальность данных после изменения статусов;
- внедряется поэтапно без глубокого рефакторинга всей архитектуры.

### Стратегию инвалидации кеша

Итоговая стратегия:
- **основная:** инвалидация по ключу при каждом изменении заказа;
- **дополнительная:** короткий TTL для списков и средний TTL для карточек;
- **операционная:** программная инвалидация по префиксу при массовых изменениях.

Контроль корректности:
- метрики `cache_hit_ratio`, `stale_read_rate`, `db_qps_after_cache`;
- алерты при падении hit ratio ниже целевого уровня;
- проверка консистентности статуса заказа после write-операции в synthetic tests.
