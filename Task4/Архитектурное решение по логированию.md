# Архитектурное решение по логированию

## Список необходимых логов

### Какие системы включаем в сбор логов

Логи приложения: 
- Shop API
- CRM API
- MES API
- CMS

Логи инфраструктуры:
- RabbitMQ
- PostgreSQL (shop db, mes db, crm db)
- S3

### INFO-логи
Ниже перечислены события, которые логируются на уровне `INFO`:

1. Аутентификация/авторизация:
   - `user_login_success`
   - `token_refreshed`
   - `permission_denied`

2. Заказ и его жизненный цикл:
   - `order_created`
   - `order_status_changed`
   - `order_price_calculated`
   - `order_sent_to_crm`
   - `order_published_to_rabbitmq`
   - `order_received_by_mes`
   - `order_completed`

3. Интеграционные события (API для внешних подключений):
   - `external_request_sent`
   - `external_response_received`
   - `message_published`
   - `message_consumed`
   - `message_requeued`

4. Изменения данных:
   - `order_updated`
   - `customer_profile_updated`
   - `inventory_reserved`

5. Операционные события внутренних сеорвисов:
   - `service_started`
   - `service_stopped`
   - `config_reloaded`
   - `background_job_started`
   - `background_job_finished`

### Базовый формат логов (JSON)
Для всех сервисов используются структурированные JSON-логи с единым набором полей:
- `timestamp`
- `level`
- `service`
- `environment`
- `host`
- `trace_id`
- `span_id`
- `request_id`
- `user_id` (если есть)
- `order_id` (если есть)
- `operation`
- `status`
- `http_status` (для API)
- `latency_ms`
- `message`


### Использование других уровней логирования
- `DEBUG`:
  - включается временно для отдельного сервиса/функции при расследовании инцидента;
  - хранится непродолжительное время (24-72 часа), по умолчанию отключен в production;
  - может включаться динамически по feature toggle.
- `WARN`:
  - частично успешные сценарии, деградация, повторные попытки, рост времени ответа, fallback;
  - примеры: `retry_attempt`, `slow_query_detected`, `circuit_breaker_open`.
- `ERROR`:
  - срывы бизнес-операций и технические ошибки;
  - примеры: `order_creation_failed`, `db_timeout`, `mq_publish_failed`;
  - обязательно содержат код ошибки, класс исключения и привязку к `trace_id`.
- `FATAL`:
  - неустранимая ошибка с остановкой процесса/подсистемы.

## Мотивация

В ситуации, когда в системе нет логов, поиск и решение проблем могут затянуться, т.к. нет достаточной информации и причинах сбоев. Это влияет как на лояльность клиентов (в худшую сторону), потерю заказов (финансовые потери) и загруженность команды, как тех. поддержки, так и разработчиков. Централизованное структурированное логирование дает сквозную наблюдаемость по пути заказа и позволяет быстро локализовать точку отказа (Shop API, CRM, очередь, MES, БД).

Что это даст компании:
- сокращение времени разбора инцидентов и более быстрый ответ клиентам;
- снижение потерь заказов и недополученной выручки;
- уменьшение нагрузки на L1/L2 поддержку за счет самостоятельного поиска по `order_id`, `user_id`, `trace_id`;
- повышение предсказуемости релизов благодаря раннему обнаружению ошибок.

### Метрики, на которые повлияет внедрение
- `MTTR` (Mean Time To Resolution) - целевое снижение на 40-60%.
- `Order Loss Rate` - доля заказов, не дошедших до финального статуса.
- `Error Rate` (доля ошибок 5xx/технических ошибок интеграции).
- Доля обращений в тех. поддержку, закрытых без привлечения тех. специалистов.

### Приоритет внедрения логирования и трейсинга
Учитывая ограниченность ресурсов, внедряем в таком порядке:

1. **Shop API + CRM API + RabbitMQ**
   - это основной транзит создания заказа и передачи в производство;
   - здесь возникают потери заказов и интеграционные ошибки.
2. **MES API**
   - фиксирует прохождение производственных этапов и статусы, критично для клиентских обращений.
3. **Shop UI + CMS**
   - позволяет связать пользовательские действия с серверными событиями и закрыть диагностические разрывы.
4. **БД и инфраструктура**
   - подключаем системные/аудит-логи для глубокого анализа.

## Предлагаемое решение

- Структурированное логирование в приложениях:
  - Java (Shop API, CRM API): `Logback/Log4j2` + JSON encoder, вывод в stdout.
  - .NET (MES API): `Serilog` + JSON sink, вывод в stdout.
- Сбор и доставка:
  - Fluent Bit на хостах/в контейнерах. Чтение stdout, парсинг JSON, отправка в брокер.
  - Буфер/шина: RabbitMQ.
- Хранение и анализ:
  - `Elasticsearch` для индексации.
  - `Kibana` для запросов и дашбордов.
- Корреляция с трейсингом:
  - прокидывание `trace_id`/`span_id` из OpenTelemetry в каждую запись лога;
  - кросс-ссылки "лог -> трейс -> метрики".

### Политика безопасности логов
- Запрещено логировать: пароли, токены, CVV, полные платежные реквизиты, персональные документы.
- Персональные данные маскируется (например, email/телефон частично), чувствительные поля хэшируются.
- Доступ по RBAC:
  - Support Role: чтение ограниченных индексов и готовых дашбордов;
  - Developer Role: расширенный доступ к техническим индексам;
  - Security Role: аудит-доступ и отчеты.
- Передача и хранение:
  - шифрование передачи с помощью SSL;
  - обязательный аудит доступа к логам;
  - доступ к прод-логам только из корпоративной сети/VPN.

### Политика хранения логов
- Отдельные индексы на систему и окружение:
  - `logs-shop-api-prod-*`
  - `logs-crm-api-prod-*`
  - `logs-mes-api-prod-*`
  - `logs-rabbitmq-prod-*`
  - и аналогично для `stage`.
- Retention:
  - Hot: 7 дней (быстрый поиск);
  - Warm: 30 дней (сжатые сегменты);
  - Cold/Archive: до 180 дней (S3 snapshot).
- Оценка объема (стартовая, с пересмотром через 2-4 недели):
  - критичные backend логи: 80-150 GB/сутки суммарно;
  - инфраструктурные/системные: 20-40 GB/сутки;
  - debug-логи в production: только временно, в отдельном short-lived индексе.
- Ограничения:
  - лимиты на размер одного события.

## Необходимые мероприятия для превращения системы сбора логов в систему анализа логов

### Алертинг (обязателен)
Нужно настроить алерты по порогам и трендам:
- всплеск `ERROR` по сервису/операции;
- рост `order_creation_failed` или `mq_publish_failed`;
- аномальный рост `permission_denied`/4xx;
- падение числа `order_created` при нормальном входящем трафике;
- резкий рост latency и timeout-событий.

Каналы уведомлений: Telegram/Slack.

### Поиск аномалий (обязателен)
Да, нужно внедрять:
- Отслеживание скорости создания заказов (например, скачок 4 -> 10 000/сек);
- Отслеживание нетипичной географии/источников запросов;
- Отслеживание всплесков одинаковых ошибок после релиза;
- Разбитие по часам/дням недели для снижения ложных срабатываний.

### Операционные процессы
- Регламент на каждый тип алерта (кто реагирует, что проверить, критерий эскалации).
- Postmortem-процесс для инцидентов P1/P2 с обновлением правил алертинга.
- Еженедельный обзор "шумных" алертов и корректировка порогов/правил.

## Критерии выбора технологии логирования
1. Производительность 
Плюсы: Fluent Bit очень легковесный, написан на C, потребляет мало CPU/RAM
Минусы: при сложных преобразованиях/парсинге может потребоваться вынос части логики в отдельный пайплайн
2. Надежность доставки
Плюсы: RabbitMQ дает очередь, ACK-модель, decoupling producer/consumer, сглаживание пиков.
Минусы: RabbitMQ не оптимален для очень больших потоков логов (по сравнению с Kafka); нужны контроль TTL, политика ретраев, обработка dead letter.
3. Масштабируемость при росте нагрузки
Плюсы: ELK масштабируется горизонтально (шарды/реплики).
Минусы: масштабирование Elasticsearch дорого по ресурсам и требует тонкой настройки.
4. Поиск и аналитические возможности
Плюсы: ELK дает мощный полнотекстовый и структурный поиск, агрегации, визуализации в Kibana.
Минусы: плохая схема индексов и неструктурированные логи резко ухудшают качество поиска и стоимость хранения.
5. Безопасность и соответствие требованиям
Плюсы: можно реализовать TLS на всех участках, RBAC в Elastic/Kibana, маскирование в Fluent Bit фильтрами.
Минусы: безопасность нужно настраивать end-to-end; по умолчанию «просто включить и забыть» нельзя.
6. Интеграция с текущей архитектурой
Плюсы: Fluent Bit универсально забирает логи контейнеров/VM, RabbitMQ уже присутствует в системах компании, ELK хорошо интегрируется с API и инфраструктурой.
Минусы: для качественной корреляции с трейсингом нужно заранее стандартизовать поля (trace_id, request_id, service, env).
