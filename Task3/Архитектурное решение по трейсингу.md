# Архитектурное решение по трейсингу

## Список данных, которые должны попадать в трейсинг
 - trace_id
 - user_id
 - request_id
 - request_time
 - subsystem
 - action
 - method
 - status
 - context

## Мотивация

В распределенных системах с асинхронным взаимодействием классические логи не дают сквозной картины. Трейсинг позволяет связать все этапы жизненного цикла заказа в единый массив, где каждый элемент содержит trace_id, таймстампы, статус и метаданные.

Метрики:
- Order Loss Rate (Коэф. потери заказов), % трейсов, не дошедших до создания заказа с рассчитаной ценой или упавших в dead_letter_queue: Прямое сокращение недополученной выручки.
- MTTR (Mean Time To Resolution), время от алерта до локализации корневой причины: Снижение простоев и нагрузки на поддержку. 
-  Latency цепочки заказа, сквозное время Shop -> CRM -> RabbitMQ -> MES -> ответ: улучшение конверсии и удовлетворенности пользователей
- Сокращение операционных расходов. Поддержка самостоятельно показывает статус заказа по trace_id или user_id.

## Предлагаемое решение

В качестве предлагаемого решения рекомендуется использовать OpenTelemetry  как де-факто отраслевой стандарт, который покрывает все слои текущей системы.

- OpenTelemetry Collector для сбора данных
- opentelemetry-java-instrumentation, подключается как Java-агент к SpringBoot-системам (Shop API, CRM API)
- OpenTelemetry.Api + OpenTelemetry.Instrumentation.AspNetCore для MES API, SDK внедряется с C#-сервис
- OpenTelemetry Web SDK, иницализация трейса с фронта (Shop UI)
- Grafana Tempo + Grafana / Jaeger, используется для хранения трейсов в S3 и просмотра трейсов через UI

[Диаграмма конттейнеров jewerly_c4_model.drawio](jewerly_c4_model.drawio)

Для реализации автоматического мониторинга и процесса анализа трейсов предлагается ввести дополнительный инструмент Span Metrics Connector. Трейсинг транслируется в агрегированные RED-метрики (Rate, Errors, Duration), по которым строятся правила, дашборды и уведомления.
Span Metrics Connector вычисляет по каждому типу агрегаций (спанов), например:
- количество вызовов
- количество вызовов со статусом ERROR
- средняя длительность прохождения всей цепочки вызовов

При появлении данных, сигнализирующих об ошибках, Grafana через инструменты уведомлений отправляет сообщение в ТГ-каналы, каналы Slack и т.д.

## Компромиссы
- Отсутствие бюджета на хранение/вычисления, в этом случае в качестве компромисса можно использовать отдельные логи приложения;
- Трейсинг заменяет архитектурный рефакторинг. Трейсинг только диагностирует. Если заказы теряются из-за отсутствия retry, некорректных архитектурных решений или ошибок в общей БД, трейсы лишь покажут проблему, но не исправят.
- Legacy code (например MES) без возможности интегрироваться с OpenTelemetry C# SDK. В этом случае, как временное решение, можно добавить ручные логи на входе/выходе HTTP/RabbitMQ.

## Аспекты безопасности

Трейсинг содержит полную картину бизнес-процессов, поэтому требует уровня защиты, сопоставимой с защитой prod-БД.

- Аутентификация и ROLE-based авторизация для доступа к трейсингу. 
- Сетевая изоляция: доступ к трейсингу только через корпоративную сеть \ VPN.
- TLS-шифрование передачи данных. 
- Если трейсинг включает реальные данные (цены, токены и т.д.), маскировать их через таблицы-справочники с ограниченным доступом. 
- S3 хранилище "сырых данных" закрыто от внешнего доступа, доступ осуществляется только по ключам, ключи периодически ротируются.
