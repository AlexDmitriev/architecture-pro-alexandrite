# Выбор и настройка мониторинга в системе

## Мотивация

Метрики миниторинга необходимы для того, чтобы получить объективную картину работы сервисов (в нашем случае - API подсистем, CMS и MES), понимание текущей ситуации с нагрузкой и процентом отказов сисетмы. Без наличия необходимых метрик мы не сможем понять источник возникающих проблем и не сможем определить варианты их решения. 


## Выбор подхода к мониторингу

1. Для MES и CMS мы будем использовать RED, как способ мониторинга различных показателей и подсистем (веб-сервисов, запросов к базам данных, очередей), тем более этот метод мониторинга допускает использование кеширования, которое мы в будущем можем внедрить.

2. Для API (MES API, CRM API, Shop API) мы будем использовать метод 4х золотых сигналов, как наиболее подходящий к API.

## Дополнительное задание
### Показатели насыщенности
- Number of message in flight in RabbitMQ - кратно больше, чем воркеров, число растет
- Number of connections for MES db instance - в районе 50% от возможных по конфигурации соединений
- Size of db instance - большее 80% от размера диска
- Number of HTTP 500 for API - более 1% от всех запросов к API
- Response time for API (для каждого API показатель свой, время постоянно выше среднего за N послених дней)
- CPU % for API - нагрузка более 40%
 
### При достижении насыщенности требуется:
- сразу уведомлять дежурного администратора
- завести тикет на investigation с высшим приоритетом
- если проблема на уровне ПО, выделить специалистов для исправления
- если проблема на уровне оборудования, попытаться масштабировать оборудования либо вертикально, добавлением ресурсов (больше памяти, процессоров, веста на диске), либо горизонтально, если это возможно при текущей архитектуре. 
- при вертикальном масштабировании создать тикет на проектирование более оптимальной архитектуры компонента
